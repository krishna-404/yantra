### Problem

`notify.sh` currently fires generic events at a placeholder workflow
(`YANTRA_NOVU_WORKFLOW` override). The operator contract (D13/D14) needs two real
workflows: instant push+email for needs-you-now moments, and a 2×/day batched digest
for review queues — following the repo's existing workflows-as-code pattern.

### Bet

If we add `yantra_needs_you` (instant, push+email) and `yantra_digest` (batched 2×/day)
workflows in `apps/backend/src/novu/workflows/` and point notify.sh's event names at
them, a parked issue pings the phone within a minute while T1 review requests batch,
verifiable by triggering each via curl and observing delivery.

### Success criteria

- [ ] Two workflow files following `user_created.workflow.ts`'s pattern, registered in `novu/workflows/index.ts`: `yantra_needs_you` (in-app+push+email, no digest, no quiet hours — D14) and `yantra_digest` (digest window aligned to two review slots).
- [ ] Payload schemas typed: {event, issue?, pr?, reason} matching what `ops/yantra/notify.sh` already sends.
- [ ] Tests per the existing notification test pattern.
- [ ] PR body documents the operator's post-merge step: `yarn workspace @connected-repo/backend novu:sync`, then set `YANTRA_NOVU_WORKFLOW` mapping obsolete (notify.sh default names match: yantra-needs-human → yantra_needs_you etc. — document the exact mapping; notify.sh itself is T3 and NOT changed here; if a rename is needed, spec it as a follow-up T3).
- [ ] All of: `yarn lint`, `yarn check-types`, `yarn test:run` green in CI.

### Out of scope

notify.sh changes (harness, T3), subscriber management UI, quiet hours (explicitly none — D14).

### Evaluation

Curl-trigger each workflow → push+email received (needs_you) and digest batches (digest). Revert condition: notification tests regress.
